# v0.3.8 review follow-up

This follow-up distinguishes reproduced behavior from deployment constraints in the supplied v0.3.7 review. The earlier [v0.3.7 report](FIXES-2026-11-04.md) describes that release; the changes below supersede its unbounded retry and TCP payload details.

## Assessment of all eight claims

1. **Running edit stops the tunnel: incorrect.** Both core-setting and spoof-pool handlers reject a running/starting/stopping instance with HTTP 409 before StopInstance. Saving a stopped/error instance intentionally invalidates pending recovery, preventing an old configuration from restarting during a save. Start must then be explicit, as the UI already explains.
2. **Unbounded recovery: confirmed.** Automatic recovery now stops after eight consecutive attempts and exposes `recovery.active`, `attempts`, `max_attempts`, `next_retry_at` and `exhausted` on dashboard/list/detail/status APIs. The UI shows pending and exhausted states. Backoff remains 1/2/4/8/16/30/30/30 seconds. Stable execution over 30 seconds resets the streak; manual Start/Restart resets it. Stop/delete cancels pending attempts. An incorrect PSK/peer allowlist normally does not exit the process; these examples in the review were inaccurate.
3. **Timestamp window: intentional security policy.** Authentication and the existing -120/+30-second acceptance window remain unchanged. `clock_skew_seconds` is the active rejected-frame diagnostic, cleared by successfully authenticated acceptable traffic. It is not a continuous NTP measurement. Synchronize server clocks; path delay/replayed authenticated frames can also affect it.
4. **Fragment-loss amplification and outer MTU: valid network constraints.** No automatic outer PMTU discovery, FEC or tunnel retransmission is added. Current IPv4 overhead is 53 bytes encrypted frame + 20 IPv4 + carrier 8 (ICMP/UDP), 20 (TCP) or 0 (4/253). With inner MTU 1280 the outer IP lengths are 1361/1373/1353 bytes respectively, excluding link headers. The review's approximate 1330 was too low. Lower the configured inner MTU if the actual path requires it. Loss of one fragment can prevent reassembly of the original datagram.
5. **Tester compatibility and SYN payload risk: confirmed.** Both panels should be upgraded. New TCP probes contain a plain SYN without data/options; see below. ICMP payload correlation is unchanged. Candidate validation failures and duplicates are exported as `rejected_probes`/`duplicate_probes`, including after completion/cancellation, and explained in the UI. A rejection can mean code/count/version mismatch, corrupt checksum or unrelated traffic from the chosen pool; the receiver cannot identify a wrong code with certainty. Each receiver run generates a fresh code when the field is empty. Reusing a code deliberately loses run isolation.
6. **Latest automatically installs the next release: incorrect.** There is no unattended updater. The installer fetches latest only when explicitly invoked; `SPOOF_RELEASE` pins a version.
7. **Real-provider and ARM64-runtime evidence missing: correct limitation.** Namespace and browser tests do not establish source-spoof acceptance by a real provider, multi-hour stability or ARM64 hardware execution. Cross compilation is not a runtime test. These require deployment access and are not reported as completed.
8. **Forwarding during TUN startup: confirmed race exposure.** A client now waits up to five seconds for its assigned interface to exist and be up. Stop cancels the wait promptly. The final socket remains bound using SO_BINDTODEVICE; no other-route fallback is introduced. This readiness wait does not assert that the peer service is listening or that the provider forwards spoofed traffic.

## Exact tester behavior

Receiver startup acknowledges success only after socket creation and timeout configuration; socket errors now return synchronously. A best-effort 4 MiB receive buffer accommodates bursts (the kernel can cap it). IPv4 and ICMP/TCP checksums are validated before correlation. Unrelated/wrong-code/count-mismatched packets and duplicate sequence numbers cannot increase a source's accepted packet count.

ICMP retains the SPT2 44-byte payload with source-bound HMAC-SHA256. TCP sends an IPv4/TCP SYN of 40 bytes with no payload or options. Ten source-port bits encode sequence 0..999. Fifteen IP-ID bits, 32 TCP-sequence bits and four source-port bits carry a 51-bit truncated HMAC of the same source/sequence/count/code. The IP-ID high bit is set so Linux IP_HDRINCL never substitutes a zero ID. This is diagnostic correlation, not a replacement for tunnel AEAD. Header rewriting/NAT can invalidate it, and a captured valid probe can be replayed once per matching run/sequence. A fresh code and per-source bitmap prevent cross-run and duplicate inflation.

A v0.3.8 receiver also accepts v0.3.7 payload-format TCP probes. A v0.3.7 receiver cannot accept new payload-free TCP probes. Upgrade both sides; use identical protocol, count and receiver code. Sender `sent_packets` means successful send syscall, not proof of arrival. Only receiver results establish observed arrival at that receiver.

## Reproducible validation

- Race-enabled Go tests: supervisor crash exhaustion, manual reset, stop cancellation, mutation serialization, stale-process telemetry, forwarder readiness timeout/cancellation, framing and checksum regressions.
- Loopback-only namespace: immediate send after receiver startup; six disjoint sources with ten packets each for ICMP/TCP; maximum 1000 packets per source; duplicate, wrong code, mismatched count and corrupted-checksum rejection; canceled sender never reports full completion.
- Pure probe tests cover all 1000 TCP sequence indexes, checksums, header/source mutations, wrong code/count, and v0.3.7 receive compatibility. Sparse IP iteration tests retain 1..100000 source coverage.
- A separate private-namespace forwarder test brings up a real TUN after the readiness wait starts, and verifies Stop cancellation and no fallback.
- Nineteen browser scenarios include rejected/duplicate counters with zero accepted IPs and supervisor recovery/exhaustion feedback.
- Release CI also runs the full existing carrier, MTU, delayed heartbeat, multi-peer, real HTTP/SQLite and installer checks before publishing both architecture packages.
